## 1. Общее впечатление

На момент ревью репозиторий не содержит исходного кода: в нём лежат `BRIEF.md`, `README.md`, ER-диаграмма (`Untitled.png`, dbdiagram.io) и wireframe-макет интерфейса (`New board 1 (1).png`, Balsamiq), поэтому ревью выполнено по проектным артефактам, определяющим будущий код. Бриф структурирован и содержит измеримые критерии приёмки, схема БД в целом нормализована и грамотно использует внешние ключи и NOT NULL-ограничения. Макет интерфейса, напротив, крайне схематичен и не покрывает MVP. Общий уровень — хорошая стадия проектирования, но без реализации проект не может быть принят.

## 2. Ключевые рекомендации

### 🔴 [Critical] В репозитории отсутствует исходный код
- **Где:** весь репозиторий (только `BRIEF.md`, `README.md`, два `.png`)
- **В чём проблема:** нет ни одного файла кода (`.py`/`.js`/`.sql`): ни скрипта инициализации БД, ни DAO, ни логики таймера, ни интерфейса.
- **Почему это важно:** ни один из 8 критериев приёмки брифа нельзя проверить; ревью кода, тестирование и сдача работы невозможны.
- **Как исправить:** добавить структуру проекта (`src/`, `tests/`, `init.sql`), реализовать MVP (CRUD проектов/задач, таймер, ручные записи, отчёт) и закоммитить код вместе с консольными тестами.
- **Источник:** найдено самостоятельно.

### 🔴 [Critical] «Блуждающий» внешний ключ у поля `tasks.name`
- **Где:** ER-диаграмма `Untitled.png`, таблица `tasks`, поле `name` (значок ссылки); третья линия связи, уходящая за правый край холста.
- **В чём проблема:** поле `name` (varchar) помечено как ссылка (Ref), и от него идёт линия связи в никуда. Две остальные связи начерчены верно (`projects.id → tasks.project_id`, `tasks.id → time_logs.task_id`), а эта — нет: внешние ключи не строятся по текстовым полям.
- **Почему это важно:** связь по тексту ломается при любом переименовании, медленнее работает и, скорее всего, является опечаткой в DBML-коде диаграммы (например, `Ref: tasks.name > ...` вместо нужного поля).
- **Как исправить:** убрать `Ref` у `name` в DBML. Если имелась в виду уникальность названий задач внутри проекта, выразить её ограничением `UNIQUE (project_id, name)`, а не ссылкой.
- **Источник:** совместно (ручная проверка линий на схеме + подсказка ИИ).

### 🟡 [Major] Деньги хранятся в типе `real`
- **Где:** ER-диаграмма, `projects.hourly_rate` (real)
- **В чём проблема:** почасовая ставка — денежное значение, хранящееся в числе с плавающей точкой.
- **Почему это важно:** двоичная арифметика float даёт ошибки округления (`0.1 + 0.2 = 0.30000000000000004`), что недопустимо в расчётах стоимости часов для счетов клиенту.
- **Как исправить:** хранить ставку в минимальных единицах как `INTEGER` (копейки: `hourly_rate_cents`) либо использовать `DECIMAL(10,2)`; конвертировать в рубли только при отображении.
- **Источник:** подсказано ИИ, принято ревьюером.

### 🟡 [Major] Пауза таймера объявлена в MVP, но не отражена ни в схеме, ни в сценариях
- **Где:** `BRIEF.md` («Таймер (старт/пауза/стоп)»), Сценарий 1; таблица `time_logs`
- **В чём проблема:** в MVP заявлена пауза, но в схеме нет никакого механизма паузы (ни поля `paused_at`/`is_paused`, ни правила разбиения лога), а Сценарий 1 описывает только «Старт» и «Стоп».
- **Почему это важно:** реализация столкнётся с неопределённостью: пауза — это разрыв внутри одной записи или несколько записей? Без решения отчёты будут считать время пауз как рабочее.
- **Как исправить:** зафиксировать в брифе и схеме одно из: (а) пауза = стоп текущего лога + старт нового (проще всего, схема не меняется); (б) накопление факта: хранить только суммарные секунды работы. Дополнить Сценарий 1 шагом «Пауза».
- **Источник:** найдено самостоятельно.

### 🟡 [Major] Риск рассинхронизации: `duration_seconds` хранится рядом с `started_at`/`ended_at`
- **Где:** ER-диаграмма, таблица `time_logs`
- **В чём проблема:** длительность — производное значение, продублированное в таблице; при обновлении `ended_at` (например, при ручном редактировании записи) `duration_seconds` может остаться старым.
- **Почему это важно:** отчёты по времени начнут расходиться с фактическими интервалами — это главный продукт трекера.
- **Как исправить:** либо не хранить длительность и вычислять её в запросе (`strftime('%s', ended_at) - strftime('%s', started_at)`), либо пересчитывать её в одном месте (Service-слой/триггер) и добавить `CHECK (ended_at IS NULL OR ended_at > started_at)`. Для активного таймера (`ended_at IS NULL`) длительность обязана быть `NULL`.
- **Источник:** подсказано ИИ, уточнено ревьюером.

### 🟢 [Minor] Противоречие в нефункциональных требованиях: «Сеть использется»
- **Где:** `BRIEF.md`, раздел 3
- **В чём проблема:** строка «Хранение данных: локально в файле БД. Сеть использется.» противоречит сама себе (очевидно, имелось в виду «не используется») и содержит опечатку.
- **Почему это важно:** из брифа непонятно, офлайн-приложение или нет; от этого зависят тесты и архитектура.
- **Как исправить:** переформулировать: «Хранение данных: локально в файле БД; сеть не используется».
- **Источник:** найдено самостоятельно.

### 🟢 [Minor] Макет интерфейса не покрывает MVP и нарушает требование о языке
- **Где:** `New board 1 (1).png` (Balsamiq)
- **В чём проблема:** на макете только три англоязычных выпадающих списка («Time: Start», «Time: Stop», «Time: Report»). Нет экранов CRUD проектов и задач, формы ручного добавления записи, диалога подтверждения удаления проекта, отчёта с фильтрами по датам.
- **Почему это важно:** критерий приёмки №7 требует русский интерфейс, а сценарии 2 и 3 вообще не прототипированы — разработчик не получит ориентира по UI.
- **Как исправить:** добавить 4–5 wireframe-экранов на русском: список проектов, список задач с кнопкой таймера, форма ручной записи (начало/окончание/комментарий), отчёт с фильтром дат, диалог подтверждения удаления.
- **Источник:** найдено самостоятельно.

### 🟢 [Minor] В схеме не предусмотрены индексы под отчётные запросы
- **Где:** ER-диаграмма, `time_logs`
- **В чём проблема:** отчёт «суммарное время по проекту/задаче за период» будет выполнять полное сканирование `time_logs`: индексы по (`task_id`, `started_at`) не заявлены.
- **Почему это важно:** требование «отчёт за день/неделю/месяц не более секунды» перестанет выполняться по мере роста объёма записей.
- **Как исправить:** `CREATE INDEX idx_time_logs_task_started ON time_logs (task_id, started_at);`
- **Источник:** найдено самостоятельно.

### 🔵 [Nitpick] Опечатки и оформление `BRIEF.md`
- **Где:** `BRIEF.md`, разделы 2, 3, 7
- **В чём проблема:** «Пользоваьтель», «Нефунциональные», «использется» с опечаткой, лишние запятые («Пользователь может, создавать»), нумерация разделов перескакивает с 3 на 6, чек-листы записаны как `[]` вместо `- [ ]`, из-за чего не отображаются как задачи.
- **Почему это важно:** снижает читаемость документа и доверие к нему.
- **Как исправить:** вычитать текст, поправить нумерацию, использовать `- [ ]` для критериев приёмки.
- **Источник:** найдено самостоятельно.

### 🔵 [Nitpick] Не задокументированы допустимые значения `status` и необязательность `client_id`
- **Где:** `projects.status`, `tasks.status` (varchar NN), `projects.client_id` (без NN)
- **В чём проблема:** статусы — свободный текст; `client_id` допускает NULL, что логично для «внутренних» проектов, но нигде не проговорено.
- **Почему это важно:** без справочника значений статусы начнут писаться вразнобой («done», «Done», «завершено»).
- **Как исправить:** добавить `CHECK (status IN (...))` или справочную таблицу; в брифе одной строкой зафиксировать, что проект может существовать без клиента.
- **Источник:** подсказано ИИ, принято ревьюером.

## 3. Что сделано хорошо

1. **Аккуратная нормализация схемы:** цепочка `clients → projects → tasks → time_logs` связана внешними ключами по целочисленным `id`, обязательные поля помечены NOT NULL, у всех сущностей есть `created_at` — хорошая база для аудита и отчётов.
2. **Элегантная модель активного таймера:** `time_logs.ended_at` допускает NULL, то есть «идущий таймер» — это запись без времени окончания. Это напрямую поддерживает правило брифа «нельзя запустить второй таймер — первый останавливается автоматически» одним запросом `UPDATE ... WHERE ended_at IS NULL`.
3. **Сильный бриф:** восемь проверяемых критериев приёмки, альтернативные потоки в сценариях и требование хранить время в UTC с отображением в локальном поясе — уровень детализации выше среднего для учебного проекта.

## 4. Расхождение с мнением ИИ

- **С чем не согласился:** ИИ на первом проходе утверждала, что связь `projects.id → tasks.name` начерчена неправильно и что ключ у `tasks.name` — ошибка уникальности. Ручная проверка линий показала: связи `projects.id → tasks.project_id` и `tasks.id → time_logs.task_id` начерчены верно, аномален только Ref у `name`. Вывод: чтение ИИ графических диаграмм нужно перепроверять вручную.
- **С чем не согласился:** совет ИИ добавить в `time_logs` необязательный `project_id` и снять NOT NULL с `task_id`, чтобы «логировать время прямо на проект». Это ломает нормализацию и создаёт второй источник правды о времени проекта; проектное время корректнее учитывать через задачи (например, служебную задачу «Оргвопросы»).
- **Что ИИ упустила, а я заметил:** пауза из MVP не отражена в схеме и сценариях; англоязычные подписи макета противоречат требованию «интерфейс на русском»; противоречие «Сеть использется»; отсутствие индексов под отчёты; скачок нумерации разделов брифа и неработающие чек-боксы.
- **Полезный инсайт ИИ:** указание на тип `real` для денежных значений и на риск рассинхронизации `duration_seconds` — оба замечания приняты в отчёт с повышением приоритета.

## 5. Итоговый рефакторинг (фрагмент схемы)

Исправленный DDL ключевых таблиц (SQLite) с учётом замечаний:

```sql
CREATE TABLE projects (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    client_id     INTEGER REFERENCES clients(id),          -- NULL = внутренний проект
    name          TEXT    NOT NULL,
    description   TEXT,
    color         TEXT,
    hourly_rate_cents INTEGER,                             -- деньги в копейках, не real
    status        TEXT    NOT NULL DEFAULT 'active'
                          CHECK (status IN ('active', 'archived')),
    created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tasks (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id  INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    name        TEXT    NOT NULL,
    description TEXT,
    status      TEXT    NOT NULL DEFAULT 'new'
                      CHECK (status IN ('new', 'in_progress', 'done')),
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (project_id, name)                              -- вместо «блуждающего» Ref у name
);

CREATE TABLE time_logs (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id    INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    started_at TIMESTAMP NOT NULL,
    ended_at   TIMESTAMP,                                  -- NULL = таймер идёт
    comment    TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (ended_at IS NULL OR ended_at > started_at)      -- защита от «конец раньше начала»
);

CREATE INDEX idx_time_logs_task_started ON time_logs (task_id, started_at);
