
# Слой бизнес-логики приложения "Моя Полка" (MyShelf)

## 1. Обзор слоя бизнес-логики

Слой бизнес-логики (Service Layer) — промежуточное звено между пользовательским интерфейсом и DAO-слоем. Он отвечает за:

- **Валидацию данных** перед записью в БД (проверка обязательных полей, диапазонов, форматов).
- **Координацию нескольких DAO-операций** в рамках одной задачи пользователя (например, добавление книги + привязка жанров и авторов — это 3 отдельных SQL-запроса, но для пользователя одна операция).
- **Применение бизнес-правил** (например, нельзя удалить справочный жанр, если он используется хотя бы в одной книге).
- **Обработку ошибок** и формирование понятных сообщений для пользователя.
- **Вычисления и агрегацию** (средняя оценка, проценты распределения).

**Принцип работы:**
```
[UI] → [Service] → [DAO] → [SQLite]
         ↑
    (валидация, правила, координация)
```

Service-слой **не знает** про интерфейс (не вызывает `print`, `tkinter` и т.д.) и **не пишет SQL напрямую** — он использует методы DAO.

## 2. Описание бизнес-операций

### Операция 1: Добавление новой книги в коллекцию

**Назначение:** Создать запись книги в БД и привязать к ней выбранные жанры и авторов.

**Входные данные:**
- `title` (str) — название книги
- `year` (int, опционально) — год издания
- `rating` (float, опционально) — оценка от 1 до 10
- `status_id` (int) — ID статуса из справочника
- `notes` (str, опционально) — заметки
- `genre_ids` (list[int]) — список ID жанров
- `author_ids` (list[int]) — список ID авторов

**Результат:**
- `int` — ID созданной книги (при успехе)
- `None` + сообщение об ошибке (при неудаче)

**Используемые SQL-запросы (через DAO):**
1. `ItemDAO.insert(...)` — INSERT INTO items
2. `RelationDAO.add_genre(item_id, genre_id)` — INSERT INTO item_genres (в цикле)
3. `RelationDAO.add_author(item_id, author_id)` — INSERT INTO item_authors (в цикле)

**Алгоритм (псевдокод):**
```
ФУНКЦИЯ add_book(title, year, rating, status_id, notes, genre_ids, author_ids):
    
    // ШАГ 1: Валидация входных данных
    ЕСЛИ title пустое ИЛИ title содержит только пробелы:
        ВЕРНУТЬ ОШИБКУ "Название книги обязательно для заполнения"
    
    ЕСЛИ rating НЕ None И (rating < 1 ИЛИ rating > 10):
        ВЕРНУТЬ ОШИБКУ "Оценка должна быть от 1 до 10"
    
    ЕСЛИ year НЕ None И (year < 1000 ИЛИ year > 2100):
        ВЕРНУТЬ ОШИБКУ "Некорректный год издания"
    
    // ШАГ 2: Создание книги
    ПОПЫТКА:
        item_id = ItemDAO.insert(title, year, rating, status_id, notes)
        ЕСЛИ item_id == None:
            ВЕРНУТЬ ОШИБКУ "Не удалось сохранить книгу в базу данных"
    
    // ШАГ 3: Привязка жанров
    ДЛЯ КАЖДОГО genre_id В genre_ids:
        RelationDAO.add_genre(item_id, genre_id)
    
    // ШАГ 4: Привязка авторов
    ДЛЯ КАЖДОГО author_id В author_ids:
        RelationDAO.add_author(item_id, author_id)
    
    // ШАГ 5: Успех
    ВЕРНУТЬ item_id

ИСКЛЮЧЕНИЕ (ошибка БД):
    ВЕРНУТЬ ОШИБКУ "Ошибка соединения с базой данных. Попробуйте позже."
```

**Проверки (валидация):**
| Поле | Правило | Сообщение при нарушении |
|------|---------|------------------------|
| title | Не пустое, не только пробелы, макс. 200 символов | "Название обязательно для заполнения" |
| rating | Число от 1.0 до 10.0 ИЛИ None | "Оценка должна быть от 1 до 10" |
| year | Целое число от 1000 до 2100 ИЛИ None | "Некорректный год издания" |
| status_id | Должен существовать в таблице statuses | "Выбран несуществующий статус" |
| genre_ids | Список ID существующих жанров | "Выбран несуществующий жанр" |

**Обработка ошибок:**
- **Ошибка валидации:** операция не начинается, пользователю показывается конкретное сообщение.
- **Ошибка БД при INSERT:** откат операции (книга не создаётся), сообщение "Ошибка сохранения".
- **Ошибка при привязке жанров/авторов:** книга уже создана, но связи не добавлены. В MVP это допустимо — пользователь может добавить жанры позже через редактирование.

### Операция 2: Редактирование существующей книги

**Назначение:** Обновить данные книги и полностью перезаписать её связи с жанрами и авторами.

**Входные данные:**
- `item_id` (int) — ID редактируемой книги
- Остальные поля — как в операции 1

**Результат:**
- `bool` — True при успехе, False при ошибке

**Используемые SQL-запросы:**
1. `ItemDAO.get_by_id(item_id)` — проверка существования
2. `ItemDAO.update(...)` — UPDATE items
3. `RelationDAO.clear_genres(item_id)` — DELETE FROM item_genres
4. `RelationDAO.clear_authors(item_id)` — DELETE FROM item_authors
5. `RelationDAO.add_genre(...)` — в цикле
6. `RelationDAO.add_author(...)` — в цикле

**Алгоритм (псевдокод):**
```
ФУНКЦИЯ update_book(item_id, title, year, rating, status_id, notes, genre_ids, author_ids):
    
    // ШАГ 1: Проверка существования книги
    existing = ItemDAO.get_by_id(item_id)
    ЕСЛИ existing == None:
        ВЕРНУТЬ ОШИБКУ "Книга не найдена"
    
    // ШАГ 2: Валидация (та же, что в add_book)
    ...
    
    // ШАГ 3: Обновление основных полей
    success = ItemDAO.update(item_id, title, year, rating, status_id, notes)
    ЕСЛИ НЕ success:
        ВЕРНУТЬ ОШИБКУ "Не удалось обновить книгу"
    
    // ШАГ 4: Полная перезапись связей
    RelationDAO.clear_genres(item_id)
    RelationDAO.clear_authors(item_id)
    
    ДЛЯ КАЖДОГО genre_id В genre_ids:
        RelationDAO.add_genre(item_id, genre_id)
    
    ДЛЯ КАЖДОГО author_id В author_ids:
        RelationDAO.add_author(item_id, author_id)
    
    ВЕРНУТЬ True
```

**Особенность:** Связи M:N не обновляются поштучно, а **полностью удаляются и создаются заново**. Это проще в реализации и исключает рассинхронизацию.

### Операция 3: Удаление книги с подтверждением

**Назначение:** Удалить книгу и все её связи (жанры, авторы) из БД.

**Входные данные:**
- `item_id` (int) — ID книги

**Результат:**
- `bool` — True при успехе

**Используемые SQL-запросы:**
1. `ItemDAO.get_by_id(item_id)` — проверка
2. `ItemDAO.delete(item_id)` — DELETE FROM items

**Алгоритм:**
```
ФУНКЦИЯ delete_book(item_id):
    existing = ItemDAO.get_by_id(item_id)
    ЕСЛИ existing == None:
        ВЕРНУТЬ ОШИБКУ "Книга не найдена"
    
    success = ItemDAO.delete(item_id)
    // Благодаря ON DELETE CASCADE в БД,
    // записи в item_genres и item_authors удалятся автоматически
    
    ВЕРНУТЬ success
```

**Бизнес-правило:** В БД настроен `ON DELETE CASCADE` для внешних ключей в таблицах `item_genres` и `item_authors`, поэтому Service-слой не должен вручную удалять связи — это делает сама БД.

### Операция 4: Поиск и фильтрация (комбинированный запрос)

**Назначение:** Найти книги по названию/автору И статусу одновременно, с сортировкой.

**Входные данные:**
- `search_query` (str, опционально) — текст поиска
- `status_id` (int, опционально) — фильтр по статусу
- `sort_by` (str) — "year" или "rating"
- `sort_order` (str) — "asc" или "desc"

**Результат:**
- `list[dict]` — список книг

**Алгоритм:**
```
ФУНКЦИЯ search_and_filter(search_query, status_id, sort_by, sort_order):
    
    // Если ничего не выбрано — вернуть все книги
    ЕСЛИ search_query == None И status_id == None:
        ВЕРНУТЬ ItemDAO.get_all_with_details()
    
    // Формирование условий
    conditions = []
    params = []
    
    ЕСЛИ search_query НЕ None:
        pattern = "%" + search_query + "%"
        conditions.append("(i.title LIKE ? OR a.name LIKE ?)")
        params.extend([pattern, pattern])
    
    ЕСЛИ status_id НЕ None:
        conditions.append("i.status_id = ?")
        params.append(status_id)
    
    // Сборка WHERE
    WHERE_CLAUSE = " AND ".join(conditions)
    
    // Валидация сортировки (защита от SQL-инъекций)
    ЕСЛИ sort_by НЕ В ["year", "rating"]:
        sort_by = "year"
    ЕСЛИ sort_order НЕ В ["asc", "desc"]:
        sort_order = "desc"
    
    // Выполнение запроса
    ВЕРНУТЬ ItemDAO.search_with_filters(WHERE_CLAUSE, params, sort_by, sort_order)
```

**Защита от SQL-инъекций:** Параметры сортировки (`sort_by`, `sort_order`) **не подставляются** через `?`, а проверяются по whitelist. Это важно, так как имена колонок нельзя параметризовать в SQL.

### Операция 5: Расчёт аналитики для дашборда

**Назначение:** Собрать все данные для экрана "Коллекция в цифрах".

**Входные данные:** нет

**Результат:**
```python
{
    "total_books": int,
    "average_rating": float,
    "completed_count": int,
    "completed_percent": float,
    "status_distribution": [{"name": str, "count": int}, ...],
    "genre_distribution": [{"name": str, "count": int}, ...]
}
```

**Алгоритм:**
```
ФУНКЦИЯ get_analytics():
    total = ItemDAO.get_total_count()
    
    ЕСЛИ total == 0:
        ВЕРНУТЬ пустой словарь с нулями
    
    avg_rating = ItemDAO.get_average_rating()
    status_dist = ItemDAO.get_distribution_by_status()
    genre_dist = ItemDAO.get_distribution_by_genre()
    
    // Найти количество завершённых
    completed = 0
    ДЛЯ КАЖДОГО item В status_dist:
        ЕСЛИ item["status_name"] == "Завершено":
            completed = item["book_count"]
    
    completed_percent = round((completed / total) * 100, 1)
    
    ВЕРНУТЬ словарь со всеми значениями
```

**Бизнес-правило:** Средняя оценка считается **только по книгам с заполненной оценкой** (WHERE rating IS NOT NULL). Кники без оценки не влияют на среднее.

## 6. Правила проектирования Service-слоя

1. **Service не знает про UI.** Он возвращает данные или выбрасывает исключения, но не вызывает `print()`, `messagebox` и т.д.
2. **Service не пишет SQL.** Все запросы инкапсулированы в DAO.
3. **Одна операция = одна транзакция.** Если добавление книги + жанров — это атомарная операция, она должна выполняться в одной транзакции (в SQLite через `conn.execute("BEGIN")` ... `conn.commit()`).
4. **Все ошибки — с понятными сообщениями.** Вместо "SQLite error: FOREIGN KEY constraint failed" пользователь видит "Выбран несуществующий статус".
